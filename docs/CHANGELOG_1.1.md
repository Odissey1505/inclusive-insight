# Inclusive Insight 1.1 — хмарне збереження та синхронізація

Це оновлення наявного додатка 1.0, а не новий проєкт. Сторінки, форми, аналітика, графіки, звіти, деморежим, резервні копії, PWA та дизайн Modern Education лишилися тими самими. Змінилися авторизація та шар збереження даних.

## Архітектура

```
UI (сторінки 1.0, без змін логіки)
   │  читають / пишуть через db/repositories.ts (як і раніше)
   ▼
IndexedDB (Dexie)  ── локальна копія даних акаунта + чернетки форм + черга змін
   ▲        │  хуки Dexie фіксують кожну локальну зміну → outbox
   │        ▼
cloud/sync.ts  ── надсилання (черга, повтори, версії) · завантаження · Realtime · конфлікти
   ▲        │
   │        ▼
Supabase PostgreSQL (RLS)  ── основне постійне джерело даних
```

- **Supabase — основне сховище.** Після входу всі записи акаунта завантажуються з хмари. Кожне збереження надсилається в хмару.
- **IndexedDB лишилася:** це локальна копія для швидкої роботи й офлайн-режиму, автозбережені чернетки форм і черга не надісланих змін. Записи 1.0 автоматично не видаляються.
- **Аналітика, Dashboard, Календар і Звіти** читають ті самі локальні таблиці, що й у 1.0. Тому формули, фільтри, періоди й графіки не змінювалися, а дані тепер приходять з хмари. Будь-яка зміна (своя чи з іншого пристрою) перераховує показники автоматично (Dexie liveQuery).

## Як працює синхронізація

| Вимога | Реалізація |
|---|---|
| Завантаження після входу | повне завантаження всіх таблиць користувача (сторінками по 1000) |
| Оновлення при поверненні до додатка | при фокусі вкладки (не частіше ніж раз на 20 с), при відновленні мережі, раз на 5 хв, кнопка «Оновити дані» |
| Realtime | `postgres_changes` для таблиць `ii_*` з фільтром `user_id`. Без Realtime усе працює через повторне завантаження |
| Без нескінченних циклів | записи з хмари виконуються в позначених транзакціях і ніколи не повертаються в чергу |
| Без дублювання | ID генерує клієнт (UUID). Повторна вставка, відповідь на яку загубилася, розпізнається (той самий ID і вміст) як успіх |
| Коректне видалення | видалення з перевіркою версії; каскад на сервері; видалене на іншому пристрої прибирається з локальної копії |
| Одночасні зміни | кожен запис має `version`. Оновлення й видалення виконуються лише за тієї версії, яку бачив пристрій. Інакше з'являється **конфлікт**, і користувач обирає: «Залишити мою версію» або «Взяти версію з хмари» |
| Офлайн | зміни зберігаються на пристрої в постійній черзі (IndexedDB), надсилаються з повторними спробами (2 с → 60 с) після відновлення зв'язку; статус «Офлайн · N у черзі», ніколи не «Збережено у хмарі» |
| Помилки | постійні помилки (RLS, відсутній батьківський запис) не відкидаються мовчки: їх видно в Налаштування → Хмара з кнопками «Повторити» / «Відкинути» |
| Зміна користувача / вихід | синхронізація зупиняється, сторінки попереднього акаунта розмонтовуються. За бажанням локальна копія видаляється з пристрою; в хмарі при цьому нічого не видаляється |
| Демодані | лишаються лише на пристрої й не синхронізуються |
| Профіль | ім'я, аватар, колір і тема синхронізуються через `ii_profiles` |

Стандартні предмети й стратегії створюються лише після першого успішного завантаження з хмари і з детермінованими ID. Тому вхід з кількох пристроїв не дублює їх.

## Перенесення локальних записів 1.0

Якщо в браузері є записи з версії 1.0, після входу з'являється банер «На цьому пристрої є записи з версії 1.0». Те саме доступне в Налаштування → Хмара → «Імпортувати локальні записи».

1. **Виявлення:** знаходяться локальні профілі 1.0 (ID `u_…`), у яких є записи.
2. **Повідомлення** з пропозицією перенести (можна відкласти).
3. **Резервна копія:** кнопка «Резервна копія» зберігає JSON локального профілю перед перенесенням.
4. **Кількість:** показано, скільки записів кожного типу буде перенесено.
5. **Підтвердження:** окремий діалог.
6. **Перенесення:** записи копіюються в акаунт і надсилаються в хмару пакетами по 200.
7. **Зв'язки:** перераховуються всі посилання (учень, урок, спостереження, завдання, подія, стратегія, ціль, вимірювання, досягнення, предмет, шаблон). Предмети й стратегії з однаковою назвою об'єднуються з наявними.
8. **Перевірка:** після надсилання дані повторно завантажуються з хмари й звіряються.
9. **Позначка:** імпорт позначається як виконаний для цього акаунта.

Захист від дублікатів: новий ID обчислюється як `stableUuid(акаунт + локальний профіль + старий ID)`. Повторний імпорт додає лише ті записи, яких ще немає.

Демодані за замовчуванням не переносяться. Для них є окремий перемикач.

Локальні записи 1.0 після перенесення **не видаляються**. Для цього є окрема кнопка «Видалити локальні записи…» з подвійним підтвердженням.

## Безпека

- **Авторизація** через Supabase Auth: реєстрація, вхід, вихід, збереження й автоматичне відновлення сесії, відновлення пароля, українські повідомлення про помилки. Сторінки без входу недоступні.
- **Ім'я** — лише поле профілю для інтерфейсу, не засіб входу.
- **RLS** на всіх таблицях: SELECT, INSERT, UPDATE і DELETE лише для `auth.uid()`, з перевіркою власника батьківських записів. Для `anon` доступу немає.
- **Ключі:** у frontend лише publishable/anon. Secret і service_role відсікаються при збірці, у застосунку та в CI.
- **Посилання з листів:** PKCE (`?code=`). Токени не з'являються в адресі, HashRouter не ламається.
- **Окремий ключ сесії** `inclusive-insight-auth`, щоб не змішуватися з іншими застосунками на тому ж `github.io`.
- **Service Worker** кешує лише файли додатка: запити до Supabase і дані користувача в Cache Storage не потрапляють.

## Перевірки

- `npm test`: **53 тести, усі пройдено**:
  - `rls.test.ts` (12): міграція виконується двічі на справжньому Postgres (PGlite), діють два користувачі. B не може прочитати, змінити, видалити дані A, створити записи під учнем, спостереженням, ціллю чи стратегією A, перенести свої рядки в акаунт A. `anon` не має доступу. Сервер сам керує версіями; застаріла версія нічого не змінює; є каскадне видалення.
  - `sync.test.ts` (12): вивантаження зі зв'язками; другий пристрій отримує все без дублювання стандартних предметів; редагування й видалення між пристроями; офлайн-черга; повторна вставка після втраченої відповіді без дублікатів; конфлікт і обидва способи його вирішення; Realtime без зворотних циклів; демодані не виходять з пристрою; ізоляція акаунтів; ІПР, досягнення й стратегії зі зв'язками; імпорт 1.0 з повторним запуском без дублікатів.
  - `cloud-config.test.ts` (11), `data.test.ts` (7), `analytics.test.ts` (11): решта, включно з усіма тестами 1.0.
- `npm run build`: без помилок; `tsc` без помилок.
- Браузерне e2e в Chrome з реальним `@supabase/supabase-js` проти локального макета Supabase API (Auth + PostgREST поверх тієї ж SQL-міграції з RLS), два окремі профілі браузера («ноутбук» і «телефон»):
  - реєстрація, неправильний пароль, вхід, збереження сесії після перезапуску браузера;
  - перенесення записів 1.0 зі збереженням зв'язків (демо не перенесено);
  - запис на ноутбуці видно на телефоні; редагування на телефоні видно на ноутбуці; видалення зникає на обох;
  - офлайн-черга з надсиланням після відновлення;
  - другий акаунт не бачить чужих записів; прямі HTTP-запити з токеном B до ID A повертають порожньо або 403 RLS;
  - відновлення пароля через посилання з листа і вхід з новим паролем;
  - перезавантаження сторінки зберігає маршрут, а після входу відкривається Dashboard;
  - звіт онлайн без попереджень; офлайн — з попередженням і обов'язковим підтвердженням;
  - регресія локального режиму: усі сторінки, PDF/DOCX/XLSX/CSV, резервна копія, мобільний вигляд, темна тема; помилок у консолі немає.

Не перевірено на справжньому проєкті Supabase, бо з цього середовища немає доступу до мережі Supabase. Зокрема, доставку Realtime-подій і листів варто перевірити після підключення (див. `SUPABASE_SETUP.md`, розділ 6).
