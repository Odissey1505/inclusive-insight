# Підключення Supabase — Inclusive Insight 1.1

Покрокова інструкція: від порожнього (або вже наявного) проєкту Supabase до робочого сайту на GitHub Pages із входом за email і синхронізацією між пристроями.

> У цій інструкції немає справжніх URL, ключів чи ідентифікаторів — підставте значення зі свого проєкту.
> Усі таблиці мають префікс `ii_`, тож Inclusive Insight можна встановити в уже наявний проєкт Supabase поруч з іншими застосунками: нічого чужого міграція не змінює.

---

## 1. Створіть таблиці та правила безпеки (SQL)

1. Supabase Dashboard → ваш проєкт → **SQL Editor** → **New query**.
2. Виконайте по черзі обидва файли з папки `supabase/migrations` (вставте вміст і натисніть **Run**):
   1. `20261118000000_inclusive_insight_1_1.sql` — основні таблиці, версії, RLS (1.1);
   2. `20261119000000_inclusive_insight_1_2_smart_schedule.sql` — розклад (1.2).

   Якщо 1.1 уже виконано, достатньо виконати лише файл 1.2.
3. Переконайтеся, що з'явилися таблиці (**Table Editor**):
   `ii_profiles, ii_students, ii_subjects, ii_strategies, ii_templates, ii_lessons, ii_observations, ii_observation_tasks, ii_observation_events, ii_strategy_uses, ii_iep_goals, ii_iep_measurements, ii_achievements` і (1.2) `ii_schedule_periods, ii_schedule_templates, ii_schedule_overrides`.
   Біля кожної має стояти позначка **RLS enabled**.

Обидві міграції можна запускати повторно: вони нічого не дублюють і не видаляють, а сторонніх таблиць не змінюють.

Якщо ви користуєтеся Supabase CLI, файл уже лежить у стандартній папці: `supabase db push`.

### Що робить міграція

| Частина | Призначення |
|---|---|
| `id uuid`, `user_id`, `created_at`, `updated_at`, `version` | обов'язкові поля кожного запису |
| `data jsonb` | повний запис у тому ж форматі, що й у додатку, тож аналітика та звіти працюють без змін |
| `student_id`, `observation_id`, `lesson_id`, `goal_id`, `strategy_id`, `subject_id`, `date`, `status` | справжні колонки для зв'язків, індексів і перевірок RLS |
| Зовнішні ключі `ON DELETE CASCADE` | видалення учня чи спостереження прибирає дочірні записи, «сиріт» не лишається |
| Тригер `ii_touch` | сервер сам керує `version` / `updated_at` і забороняє змінювати `user_id` та `created_at` |
| RLS (SELECT / INSERT / UPDATE / DELETE) | користувач бачить і змінює лише рядки, де `user_id = auth.uid()` |
| Перевірка батьківських записів | не можна створити урок, завдання, вимірювання чи застосування стратегії під чужим учнем, спостереженням, ціллю або стратегією |
| `revoke ... from anon` | без входу таблиці недоступні навіть для читання |
| Публікація `supabase_realtime` | миттєве оновлення між відкритими пристроями (Realtime враховує RLS) |

## 2. Налаштуйте Authentication

Supabase Dashboard → **Authentication**.

1. **Sign In / Providers → Email**: має бути увімкнено (Enabled).
   - **Confirm email**: рекомендовано залишити увімкненим. Тоді після реєстрації користувач отримує лист і входить після підтвердження. Додаток показує відповідне повідомлення.
   - **Minimum password length**: 8 (додаток теж вимагає щонайменше 8 символів).
2. **URL Configuration**:
   - **Site URL**: адреса сайту, наприклад `https://USERNAME.github.io/REPOSITORY/`.
     Якщо проєкт Supabase спільний з іншим застосунком і Site URL уже зайнятий, залиште його як є: Inclusive Insight завжди передає власну адресу повернення.
   - **Redirect URLs**: додайте
     - `https://USERNAME.github.io/REPOSITORY/**`
     - `http://localhost:5173/**` (локальна розробка)
     - `http://localhost:4173/**` (`npm run preview`)
3. **Emails**: стандартні шаблони підходять. Посилання з листів повертають користувача на `…/REPOSITORY/?ii=confirmed&code=…` або `…/?ii=recovery&code=…`. Додаток обмінює код на сесію (PKCE), прибирає параметри з адреси й відкриває Dashboard або вікно нового пароля. Маршрутизація `#/…` при цьому не ламається.
4. **SMTP**: вбудована пошта Supabase має жорсткі ліміти (кілька листів на годину) і призначена для тестування. Для реальної роботи підключіть власний SMTP: **Authentication → Emails → SMTP Settings**.

Важливо: посилання з листа (підтвердження чи відновлення пароля) потрібно відкривати в тому самому браузері, де його запитали. Так працює захищений PKCE-обмін. Якщо відкрити в іншому, додаток пояснить, що треба увійти з паролем або запросити новий лист.

## 3. Передайте URL і publishable key у збірку

Потрібні дві змінні: `VITE_SUPABASE_URL` (`https://<project-ref>.supabase.co`, без `/rest/v1/`) і `VITE_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_…`). Їх можна передати двома способами.

**Рекомендовано: Variables репозиторію GitHub.** Settings → Secrets and variables → Actions → вкладка **Variables** → **New repository variable**. Створіть обидві змінні з точно такими назвами. Цей спосіб не залежить від прихованих файлів. Замість Variables можна використати **Secrets** з тими самими назвами: вони мають пріоритет.

**Або файл `.env` у корені репозиторію** з тими самими двома рядками. Назва файлу починається з крапки, тож Finder і Провідник його приховують, і при завантаженні папки через веб-інтерфейс GitHub він часто не потрапляє в репозиторій. Перевірте, що `.env` видно у списку файлів на GitHub.

Крок `Configure Supabase` у workflow виконується **до** тестів і збірки. Він обирає джерело в порядку Secrets → Variables → `.env` і пише в журнал лише режим і джерело, без значень:
- `Supabase: CLOUD mode, configuration from repository variables (values hidden).` — усе гаразд;
- попередження `Supabase not configured` — сайт збереться в **локальному режимі**; додайте Variables і перезапустіть workflow;
- помилка `Secret Supabase key` — у змінній опинився secret- чи service_role-ключ; workflow зупиняється. Замініть його на publishable і відкличте секретний ключ у Supabase.

Publishable key за задумом публічний: він лише вказує на проєкт, а дані захищає RLS. **Ніколи** не використовуйте **secret** (`sb_secret_…`) чи **service_role** ключ. Його відхиляють і збірка (`vite.config.ts`), і крок `Configure Supabase`, і перевірка бандла (`scripts/check-bundle.mjs`).

Тести не залежать від цих змінних: логіку конфігурації перевіряють на тестових значеннях-заглушках з налаштуваннями і без них.

## 4. Локальна розробка

```bash
npm install
npm run dev                    # http://localhost:5173 (з Supabase, якщо є .env або .env.local)
```

Щоб запустити локальний режим 1.0 без хмари, створіть `.env.local` з порожніми значеннями `VITE_SUPABASE_URL=` і `VITE_SUPABASE_PUBLISHABLE_KEY=`.

---

## 5. GitHub Pages

1. **Settings → Pages → Source: GitHub Actions**.
2. Зробіть push у `main`. Workflow `.github/workflows/deploy.yml` виконає по черзі:
   - `npm ci`;
   - `Configure Supabase` (Secrets → Variables → `.env`);
   - тести, зокрема перевірку RLS на справжньому Postgres (PGlite);
   - збірку;
   - перевірку бандла на секретні ключі;
   - публікацію.
3. Додайте адресу сайту до **Redirect URLs** у Supabase (див. крок 2).

**Окремий ключ сесії.** Кілька застосунків на одному `USERNAME.github.io` мають спільне сховище браузера. Тому Inclusive Insight зберігає сесію під власним ключем `inclusive-insight-auth`. Вхід у цей додаток не впливає на сесії інших ваших застосунків з тим самим проєктом Supabase, і навпаки.

---

## 6. Перевірка після налаштування

1. Відкрийте сайт → **Зареєструватися** → підтвердіть email → увійдіть.
2. Створіть учня та спостереження. Індикатор угорі має показати «Збережено у хмарі».
3. У Supabase **Table Editor** → `ii_observations` має з'явитися рядок з вашим `user_id`.
4. Увійдіть з телефона тим самим акаунтом: запис має бути на місці.
5. Створіть другий акаунт. Він не повинен бачити записів першого.
6. **Налаштування → Хмара**: підключення «підключено», Realtime «увімкнено».

### Якщо щось не так

| Симптом | Причина / рішення |
|---|---|
| «Таблиці Inclusive Insight не знайдено» | не виконано SQL з кроку 1 |
| Після входу з листа «Посилання застаріло» | посилання вже використане або минуло; запросіть новий лист |
| Лист не приходить | ліміт вбудованої пошти; підключіть SMTP |
| `redirect_to` не дозволено / повертає на інший сайт | адреси немає в Redirect URLs |
| Realtime «недоступно» | дані все одно оновлюються при поверненні в додаток і кнопкою «Оновити дані»; перевірте, що таблиці додано в публікацію `supabase_realtime` (Database → Publications) |
| «Доступ заборонено правилами безпеки (RLS)» | запис посилається на чужі або видалені дані; деталі в Налаштування → Хмара → «Зміни, які не вдалося надіслати» |
